### Designing a Modern Cross-Platform Low-Level Graphics Library

그래픽스 API는 초기의 3D 가속기에서 설정 가능한 몇몇 단계만 제한적으로 제어할 수 있는 작은 명령 집합에서 출발해, 현재는 하드웨어의 거의 모든 측면을 드러내는 매우 저수준의 프로그래밍 인터페이스로 발전해 왔습니다.
차세대 API인 마이크로소프트의 Direct3D12와 크로노스 그룹의 Vulkan은 비교적 새롭게 등장했으며, 하드웨어 벤더들로부터 이제 막 널리 채택되고 지원되기 시작했습니다. 반면 Direct3D11과 OpenGL은 여전히 업계 표준으로 간주됩니다.

새로운 API는 성능과 기능 면에서 상당한 향상을 제공할 수 있지만, 구형 하드웨어에서는 지원되지 않을 수 있습니다. 따라서 폭넓은 플랫폼을 대상으로 하는 애플리케이션이라면 Direct3D11과 OpenGL을 지원해야 합니다. 또한 새로운 API를 기존의 낡은 패러다임과 함께 사용한다면 아무런 이점을 얻을 수 없습니다. 예를 들어, 기존 렌더러에 Direct3D12 지원을 추가하면서 Direct3D11 인터페이스를 Direct3D12로 구현하는 것은 충분히 가능하지만, 그로 인한 성능이나 구조적 이득은 전혀 없습니다.

대신, 차세대 API가 제공하는 유연성을 활용할 수 있는 새로운 접근 방식과 렌더링 아키텍처가 앞으로 개발될 것으로 기대됩니다.

교차 플랫폼 3D 애플리케이션이 지원해야 할 API는 최소 네 가지(Direct3D11, Direct3D12, OpenGL/GLES, Vulkan)이며, 여기에 iOS와 macOS 플랫폼을 위한 Apple의 Metal까지 더해집니다.
모든 API마다 별도의 코드 경로를 작성하는 것은 실제 애플리케이션에서는 현실적으로 불가능하므로, 교차 플랫폼 그래픽스 추상화 계층이 필요하다는 점은 명백합니다.

#### 경량 추상화 
* 애플리케이션이 가능한 한 모든 저수준 기능을 활용할 수 있도록, `API`는 기본 네이티브 `API`에 최대한 가깝게 설계되어야 합니다. 그러나 각 `API`가 노출하는 특정 기능이 상당히 다를 수 있기 때문에, 이 요구 사항을 충족하는 것은 많은 경우 어려운 과제입니다.

#### 낮은 성능 오버헤드
* 추상화 계층은 성능 측면에서 효율적이어야 합니다. 만약 상당한 오버헤드를 도입한다면, 그것을 사용하는 의미가 없습니다.

#### 편의성
* API는 사용하기에 편리해야 합니다. 개발자가 그래픽 하드웨어에 대한 제어를 제한하지 않으면서, 목표를 달성할 수 있도록 도와주어야 합니다.

#### 멀티스레딩
* 작업을 효율적으로 병렬화할 수 있는 능력은 Direct3D12와 Vulkan의 핵심이자, 새로운 API들의 주요 장점 중 하나입니다. 따라서 교차 플랫폼 계층에서 멀티스레딩 지원은 필수입니다.

#### 확장성
* API가 아무리 잘 설계되더라도 일정 수준의 추상화는 불가피합니다. 특정 기능을 구현하는 가장 효율적인 방법이 네이티브 API를 직접 사용하는 것인 경우도 있습니다. 추상화 계층은 기본 네이티브 API와의 매끄러운 상호 운용성을 제공해야 하며, 애플리케이션이 누락된 기능을 추가할 수 있는 방법을 마련해야 합니다.

---

이 글에서는 이러한 문제를 해결하기 위해 설계된 경량 교차 플랫폼 그래픽스 API 추상화 계층인 Diligent Engine을 소개합니다.
이 엔진의 주요 목표는 Direct3D12와 Vulkan 같은 차세대 API의 장점을 활용하면서도, 동시에 Direct3D11, OpenGL, OpenGLES를 통해 구형 플랫폼도 지원하는 것입니다.
Diligent Engine은 모든 지원 플랫폼에 대해 공통된 C++ 프론트엔드를 제공하며, 기본 네이티브 API와의 상호 운용성도 지원합니다. 또한 Unity와의 통합을 지원하며, 독립형 게임 엔진, Unity 네이티브 플러그인, 기타 3D 애플리케이션의 그래픽스 서브시스템으로 사용되도록 설계되었습니다. 전체 소스 코드는 GitHub에서 다운로드할 수 있으며 자유롭게 사용할 수 있습니다.

#### Overview
* Diligent Engine API는 Direct3D11과 Direct3D12의 일부 기능을 가져오면서, 동시에 플랫폼 특유의 세부 사항을 감추고 시스템을 쉽게 사용할 수 있도록 새로운 개념을 도입합니다.
이 API는 다음과 같은 주요 구성 요소들을 포함합니다:

#### 렌더 디바이스(IRenderDevice 인터페이스)
* 텍스처, 버퍼, 셰이더, 파이프라인 상태 등 모든 다른 객체들을 생성하는 역할을 담당합니다.


#### 디바이스 컨텍스트(IDeviceContext 인터페이스)
* 렌더링 명령을 기록하는 주요 인터페이스입니다. Direct3D11과 유사하게, 즉시(immediate) 컨텍스트와 지연(deferred) 컨텍스트가 존재합니다(이들은 D3D11 구현에서 해당 컨텍스트 타입에 직접 매핑됩니다).
즉시 컨텍스트는 커맨드 큐와 커맨드 리스트 기록 기능을 결합한 형태로, 명령들을 기록하고 충분한 수의 명령이 쌓이면 커맨드 리스트를 실행에 제출합니다. 반면 지연 컨텍스트는 오직 커맨드 리스트 기록만을 수행하며, 기록된 리스트는 즉시 컨텍스트를 통해 실행에 제출됩니다.

* API를 설계하는 또 다른 방식은 커맨드 큐와 커맨드 리스트를 직접 노출하는 것이지만, 이 방식은 Direct3D11과 OpenGL에는 잘 맞지 않습니다. 또한 동적 디스크립터 할당(dynamic descriptor allocation) 같은 일부 기능은 특정 스레드에서 특정 지연 컨텍스트가 커맨드 리스트를 기록한다는 사실이 보장될 때 훨씬 효율적으로 구현될 수 있습니다.

* Diligent Engine이 취한 접근 방식은 확장성을 제한하지 않습니다. 애플리케이션은 스레드마다 하나의 지연 컨텍스트를 생성하는 것이 기대되며, 내부적으로 각 지연 컨텍스트는 락프리(lock-free) 방식으로 커맨드 리스트를 기록합니다. 동시에 이 접근 방식은 구형 API와도 잘 호환됩니다.

* 현재 구현에서는 기본 그래픽스 커맨드 큐를 사용하는 단 하나의 즉시 컨텍스트만 생성됩니다. 다중 GPU나 여러 유형의 커맨드 큐(예: compute, copy 등)를 지원하려면, 각 큐마다 하나의 즉시 컨텍스트를 두는 것이 자연스러운 확장 방식입니다. 이 경우 컨텍스트 간 동기화 유틸리티가 필요하게 됩니다.

#### 스왑 체인(ISwapChain 인터페이스)
* 스왑 체인 인터페이스는 백 버퍼(back buffer)들의 체인을 나타내며, 최종적으로 렌더링된 이미지를 화면에 표시하는 역할을 담당합니다.
렌더 디바이스, 디바이스 컨텍스트, 그리고 스왑 체인은 엔진 초기화 과정에서 생성됩니다.

#### 리소스(ITexture 및 IBuffer 인터페이스)
* 리소스는 텍스처와 버퍼 두 가지 유형으로 나눌 수 있습니다.
텍스처에는 2D 텍스처, 3D 텍스처, 텍스처 배열, 큐브맵(cubemaps) 등 다양한 형태가 있으며, 이들은 모두 ITexture 인터페이스로 표현할 수 있습니다.

#### 리소스 뷰(ITextureView 및 IBufferView 인터페이스)
* 텍스처와 버퍼가 단순히 데이터를 담는 컨테이너라면, 텍스처 뷰와 버퍼 뷰는 그 데이터가 어떻게 해석되어야 하는지를 정의합니다.
예를 들어, 하나의 2D 텍스처는 렌더링 명령을 위한 렌더 타겟으로 사용될 수도 있고, 셰이더 리소스로 사용될 수도 있습니다.

#### 파이프라인 상태(IPipelineState 인터페이스)
* GPU 파이프라인에는 깊이-스텐실, 래스터라이저, 블렌드 상태, 다양한 셰이더 단계 등 많은 설정 가능한 스테이지가 포함되어 있습니다.
Direct3D11은 모든 스테이지 파라미터를 한 번에 설정하기 위해 대규모 객체를 사용합니다(예: 래스터라이저 객체는 모든 래스터라이저 속성을 포함). 반면 OpenGL은 각 스테이지의 개별 속성을 세밀하게 제어하기 위해 수많은 함수를 제공합니다. 그러나 두 방식 모두 실제로는 모든 상태가 내부적으로 하나의 단일 상태로 결합되는 최신 그래픽 하드웨어와는 잘 맞지 않습니다.
Direct3D12는 파이프라인 상태 객체를 API에서 직접 노출하며, Diligent Engine도 같은 방식을 사용합니다.

#### 셰이더 리소스 바인딩(IShaderResourceBinding 인터페이스)
* 셰이더는 GPU에서 실행되는 프로그램입니다. 셰이더는 다양한 리소스(텍스처와 버퍼)에 접근할 수 있으며, 셰이더 변수와 실제 리소스를 연결하는 과정을 리소스 바인딩이라고 합니다.
리소스 바인딩의 구현 방식은 API마다 크게 다릅니다. Diligent Engine은 셰이더 리소스 바인딩이라는 새로운 객체를 도입하여, 특정 파이프라인 상태에서 모든 셰이더가 필요로 하는 모든 리소스를 하나로 묶어 관리할 수 있도록 합니다.
